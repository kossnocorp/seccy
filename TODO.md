# Seccy roadmap

## Hardware backends and authorization policies

- [x] Draft a unified [provider/configuration design](docs/strategy-config-design.md) covering current and planned providers, portable bindings, OS/host selectors, overlays, provisioning/rotation, integrations and sessions. The configuration foundation is implemented; new hardware backends remain planned. See [current support](docs/providers.md).
- [x] Review and implement the proposed provider resolver and capability catalog, starting with adapters for existing `secure-enclave` and `tpm-fido2-hmac` behavior. Keep the portable-encryption decision and other open decisions explicit; do not auto-migrate existing keys to stronger or weaker policies.
- [x] Support inline provider declarations and per-key provider parameters (`kind`, `auth`, `mode`, `verify`, `slot`, `algorithm`) using the same validation as named providers. Inline key `kind` bypasses the root selector; key `kind` and `provider` are mutually exclusive. Parameter overrides resolve key → selected provider → implementation defaults, with root `mode` before the final prompt default. Preserve valid legacy prompt/notify configs, including per-key `mode = "notify"`, and test overlay conflicts, incompatible fields and immutable-binding drift.
- [ ] Introduce global defaults and per-key overrides for a **backend** (where the private key lives) and an **authorization policy** (what permits its use). Integrate the portable FIDO secrets credential design with this schema, keeping logical key handles, immutable credential bindings, backend selection and authorization distinct. Prefer explicit validated combinations over arbitrary storage/auth cross-products. Use reusable `[providers.device]` definitions referenced by `keys.auth.provider = "device"` and root/per-key inline OS or host selectors for shared dotfiles (replacing the earlier abstract `machine` proposal). Omitted selection or `"default"` resolves to Secure Enclave on macOS and to no provider on Linux; unresolved key operations must fail until configured explicitly. A key inherits the root selector unless overridden. Use `provider` / `[providers]` as the agreed user-facing names, with `kind` selecting the implementation. Resolve TPM authorization explicitly on Linux/PC (FIDO, PIV, etc.). Do not assume every TPM has the same authorization setup, silently weaken policy, or replace keys when profiles change. Evaluate defaults, local overrides, capability validation, bootstrap behavior and migrations before choosing the most secure, concise design; the resolver and existing adapters are implemented; portable binding creation, hardware probing and migrations remain pending.
- [ ] Document each supported combination in `docs/providers/<backend>-<authorization>.md`: provisioning, firmware/protocol requirements, key export guarantees, private operations, user verification, fallback, recovery, migration, and trust boundary.
- [ ] Support these eligible combinations, distinguishing production from experimental and signing-only from decryption-capable:
  - Secure Enclave + per-operation biometric authorization (signing and key agreement/decryption).
  - Native FIDO SSH security keys + mandatory user presence and verification (SSH authentication and SSHSIG/Git signing only).
  - Direct PIV + PIN Always and Touch Always on YubiKey 5/5 FIPS (on-device key generation; signing and decryption/key agreement).
  - Direct PIV + MatchAlways on supported Bio Multi-protocol devices; enforce touch on PIN fallback and document that MatchAlways is not fingerprint-only.
  - TPM + fresh FIDO assertion verified by an isolated Seccy authorization service (signing and key agreement; service is trusted to enforce approval).
  - TPM + PIV PolicySigned authorization bound to a fresh TPM session and exact command (signing and key agreement).
  - TPM + FIDO previewSign PolicySigned authorization, experimental and capability-gated.
  - Direct FIDO previewSign P-256 signing, experimental and signing-only.
  - Direct OpenPGP with keys generated on-device and per-operation touch; validate PIN policies separately for signing, authentication and decryption slots.
- [ ] Rework current FIDO hmac-secret + TPM flow: remove reusable authorization secrets from the user process. Extend `seccy-tpm` to own enrollment bindings, generate single-use operation-bound challenges, verify FIDO signatures/RP/UP/UV, and authorize TPM operations through PolicySigned. Protect enrollment changes as carefully as key use. Document service/kernel compromise and optional remote-broker tradeoffs.
- [ ] For PolicySigned, disable password/HMAC authorization bypasses, bind nonceTPM and cpHashA, enforce expiry/session consumption, test replay/substitution, and use separate narrowly scoped signing and decryption keys. Hardware-back the policy authority where feasible; its use remains subject to the service trust boundary.
- [ ] Add native FIDO SSH support, including Git SSHSIG and enforced UP/UV. Hardware-held credential handles are not exported private keys.
- [ ] Add direct PIV and TPM + PIV support, metadata/attestation checks and on-device generation. Do not import software-generated private keys into a profile claiming "never exportable".
- [ ] Add `preview = false` by default, with explicit opt-in for direct and TPM-mediated previewSign. Probe firmware/extensions/algorithms. Yubico labels previewSign non-production; firmware 5.8 is not available on current 5 FIPS devices and installed firmware cannot be upgraded.
- [ ] Add ordinary P-256 SSH/Git signatures for new backends. Existing Secure Enclave/TPM P-256 signing is not preview; only previewSign-dependent paths require preview opt-in.
- [ ] Add OpenPGP support; distinguish OpenPGP-format Git signatures from SSHSIG. Validate per-slot confirmation and middleware caching behavior.
- [ ] Enforce PIN verification plus fresh touch, or fresh fingerprint, for every relevant private operation. Disable consent caches/batching in strict profiles. PIN re-verification does not prove fresh human typing; hosts can cache PINs. Never silently fall back to weaker authorization or software keys.
- [ ] Validate backend + authorization + hardware/firmware + algorithm + mode at config load/provision/use, returning actionable errors. Detect Bio FIDO vs Bio Multi-protocol; do not infer capability from marketing names. Strict profiles must reject notify-only operation.
- [x] Separate reusable aliases from immutable SHA-256 physical key IDs; add same-name rebuilding with explicit mode changes, retain old decryption generations, and identify GitHub titles with short xxHash32 suffixes while comparing full public keys.
- [ ] Extend explicit replacement to backend changes once backend/authorization strategies are implemented. Validate generation creation and recovery on real Secure Enclave and TPM/FIDO hardware, including biometric enrollment changes; mocks cannot establish hardware enforcement.
- [ ] Keep FIDO-encrypted software private keys outside strict profiles: they expose the private key in RAM. PRF-based symmetric encryption also does not provide public-recipient-only encryption. Track weaker optional profiles separately if ever added.

## Secrets

- [ ] Extend the initial macOS multi-recipient secrets envelope to other eligible hardware backends; consider actual age interoperability/plugin support separately from age-style semantics.
- [ ] Add portable hardware identities for macOS secrets, initially targeting FIDO2-capable security keys. First settle the provider/backend and authorization schema above, and explicitly choose the encryption tradeoff below. Do not infer decryption capability or removability from `fido2` alone: it is a protocol, and supported extensions vary by authenticator.

### Portable-key bootstrap workflow

- [ ] Support cloning a dotfiles repository onto a fresh machine, inserting an already enrolled security key, and decrypting repository secrets to generate configuration files without first running `seccy provision`, creating a machine key, or depending on a pre-existing local key registry/agent. Define how the initial portable identity is selected before global configuration exists; avoid a circular dependency where that configuration is itself an encrypted secret. Reuse `SECCY_IDENTITY` / `--identity` / `-i` with the existing environment-over-flag precedence and no silent fallback.
- [ ] Separate logical identity names from portable credential bindings. Design concise, validated config fields for the provider and its public metadata: for FIDO2, the credential ID, relying-party ID, verification public key, and any required extension parameters; for other providers, their corresponding immutable identity information. A device label is a UX hint, not cryptographic identity; USB paths, model names and AAGUIDs must not identify a unique credential. Public bindings may travel with dotfiles, but PINs, derived secrets and plaintext private keys must never be written there.
- [ ] Separate one-time credential creation from attaching an existing credential and from enrolling a public recipient in a secrets file. Repeated provisioning/enrollment must reuse and verify the recorded binding, never replace a removable-device credential merely because local state is absent. Reject incompatible provider changes and name collisions; require an explicit migration/replacement workflow. A missing device must produce an actionable insert-the-correct-key prompt, not trigger creation of a substitute identity.
- [ ] After bootstrap, let the user explicitly create/enroll the machine's Secure Enclave recipient, use the portable identity to re-encrypt repository secrets for both recipients, and commit only the updated encrypted data and public metadata. Distinguish creating the new machine key from provisioning all configured keys. Preserve portable-key access as recovery, make re-encryption atomic, and verify that later decryption works using the machine identity with the removable key disconnected.
- [ ] Require fresh user verification and presence for each relevant FIDO operation: PIN plus touch, or supported built-in biometric verification. Validate extension and policy support, verify assertion signatures/challenges/RP/UP/UV, and reject unsupported combinations without downgrading. Keep secrets prompts distinct from SSH/signing prompts; support piped secret input without consuming it for PIN entry. Document cancellation, lost/reset devices, backup recipients, hardware compatibility, and the limits of host-memory protection.
- [ ] Test fresh-machine use without registry state, environment/flag selection, wrong or missing authenticators, unsupported extensions, repeated provisioning, binding substitution, mixed recipients, cancelled/failed atomic re-encryption, and preservation of existing Secure Enclave behavior. Include real-device validation before claiming hardware support; mocks alone cannot establish PIN/touch/biometric enforcement.

### Decision required: portable secrets encryption provider

See the [unified design](docs/strategy-config-design.md) for proposed names, binding lifecycle, compatibility rules and implementation order.

The desired properties are portable decryption, encryption using only public recipients, and no long-term private decryption key exposed to host memory. Ordinary FIDO2 `hmac-secret` cannot provide all three together. Select supported providers and their explicit guarantees before implementing the credential/envelope format; no option has been selected yet.

| Option | Advantages | Costs and limitations |
| --- | --- | --- |
| Direct FIDO2 `hmac-secret` symmetric wrapping | Portable credential; no software asymmetric decryption key to store or reconstruct; can coexist with Secure Enclave recipient wrappers. | The authenticator is needed to encrypt as well as decrypt its recipient wrapper, including re-encryption that retains it. Derived symmetric material enters host memory, so this is not an all-key-material-stays-in-hardware guarantee. Require extension support and fresh UP/UV; do not assume every YubiKey/Bio/FIPS model supports the same combination. |
| FIDO2-protected software encryption identity | Preserves public-recipient-only encryption while requiring the authenticator to unlock decryption on a new machine. | A software private decryption key is unwrapped or reconstructed in host memory. This conflicts with the strict never-exportable-private-key requirement and must be an explicitly separate, weaker provider if offered. The encrypted identity and credential binding must remain portable and recoverable. |
| On-device PIV encryption/key-agreement identity | Portable hardware identity with public-recipient-only encryption; a private key generated on-device remains in hardware during decryption/key agreement. | Requires PIV-capable hardware and middleware, not merely FIDO2 support; FIDO-only Bio devices cannot use it. Validate algorithm support and per-operation PIN/touch or biometric policies. Payload keys and plaintext still enter host memory, as with Secure Enclave envelope encryption. |

- [ ] Decide whether to offer multiple explicitly named providers, which qualify for strict profiles, and whether direct FIDO2 symmetric wrapping's requirement to insert the key while writing secrets is acceptable. Document the distinction between a hardware-held credential/root secret, a derived wrapping secret, a persistent asymmetric private key, and an ephemeral payload key. Never present the options as providing equivalent export guarantees.

### Authenticated sessions

- [ ] Explore `seccy secrets session -- <command>`: authenticate a scoped session without exporting secrets up front; subsequent `get` calls within that session notify instead of prompting. Define OS-authenticated process scope, expiry, revocation, child inheritance, concurrency and replay protection. An environment variable alone must not be an authorization capability. Explain that hardware per-operation biometric/UV policies may prevent this mode; do not weaken strict keys silently. Explicit get still reveals plaintext to its caller.

## CLI configuration and integrations

- [ ] Complete forge integration (key fields, validation, GitHub role derivation and permission enforcement are implemented; GitLab publication remains pending): `use` accepts one permission string or a nonempty list; both keys and approval credentials use `name` for display text. Add per-key `forge = "github"` or `forge = ["github", "gitlab"]`, deriving publication roles from explicit `use`. Deprecate `github`/`gitlab` role fields while preserving compatibility; accept GitLab scalar roles or `["auth", "signing"]` and map the pair to `auth_and_signing`. Reject conflicting old/new fields and unsupported roles/formats. Migration must not silently broaden remote registration, including when different forges previously had different roles. Test normalization, overlays, combined roles, secrets-only rejection, provider capabilities and JSON/jq deprecation diagnostics.
- [x] Add `config.local.toml`, global `secrets.local.toml`, and hierarchical `seccy.local.toml` overlays. At each directory load the base file first, then its local counterpart; traverse ancestors from root toward cwd after global defaults. A closer base file overrides both base and local values from higher directories. Discover local-only directories too. For the example files B=`code/seccy.toml`, A=`code/seccy.local.toml`, C=`project_name/seccy.toml`, D=`pkgs/pkg_name/seccy.local.toml`, E=`scripts/seccy.toml`, apply B → A → C → D → E. Specify field/table merge semantics, provenance, recipient conflict validation, explicit `--secrets`/`--global` behavior, mutation targets and picker behavior; preserve the distinction between portable public credential bindings and machine-local selections. Add precedence and local-only discovery tests and document gitignore recommendations.
- [x] Add global configuration-path overrides: `--config PATH` (`-c`; also support the requested `--c` alias) and `--global-secrets PATH` (`--gs`). Resolve these once for all dependent commands, rather than treating them as project-file selection. `seccy provision -c ./seccy.config.toml` must read that key config; `seccy s set -g GLOBAL_SECRET -c ./seccy.config.toml` must use the selected key config. `--global-secrets` must replace the global secrets path both during hierarchical discovery and for `-g` operations. Document independent defaults/precedence; specifying `--config` must not silently redirect secrets to an unrelated path.
- [ ] Add GitLab CLI integration through `seccy glab ...`, including `seccy glab sync`, matching the GitHub integration's key reconciliation and fingerprint naming. Document `glab` authentication, GitLab host selection, required API scopes/permissions, and authentication/signing key support. Test self-managed hosts, rotation, duplicates and error reporting.
